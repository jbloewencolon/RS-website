# Editing this site's copy — a map, not a tutorial

This site has ten public pages, and they are not all edited the same
way. Which method applies to a given page determines how risky an
edit is and how much HTML/CSS familiarity it requires. This document
exists so that's a lookup, not a guess.

## The three tiers

Ten pages, three real risk levels — not two. "Generated by Hugo"
and "safe for someone without HTML experience to edit" turn out to be
different properties, and conflating them would make this guide
actively misleading, so they're kept separate below.

### Tier 1 — YAML-driven, safe to edit without touching HTML

`Learn.dc.html`, `Archive.dc.html`, `BehindTheScenes.dc.html`, and
`Resources.dc.html` are generated by [Hugo](https://gohugo.io) from
plain data files, and — this is the part that actually matters here —
their content genuinely lives in those data files, as plain text
fields with no markup. This is the only tier where "edit a YAML file,
don't touch HTML" is a true description of the whole job.

1. Open the relevant file in `hugo/data/` (see the table below).
2. Edit the text field. Keep quotes around any value containing a
   colon, and keep the indentation exactly as it is — YAML is
   whitespace-sensitive.
3. Run `npm run build:hugo` from the repo root. This regenerates the
   matching `.dc.html` file at the repo root and overwrites it.
4. Run `npm run build && npm run check`. Both must pass clean before
   the change is done — `check` catches broken HTML, accessibility
   regressions, and CSP violations automatically.

| Page | Data file(s) | What lives there |
|---|---|---|
| `Learn.dc.html` | `hugo/data/principles.yaml`, `topics.yaml`, `opacity.yaml`, `terms.yaml` | The thirteen principles, Learn's topic list, opacity clauses, Taíno-term disclosures |
| `Archive.dc.html` | `hugo/data/archive.yaml` | Every citation: title, author, tags, why it's included, where to read it |
| `BehindTheScenes.dc.html` | `hugo/data/substrate.yaml`, `faults.yaml`, `changelog.yaml`, `crawler.yaml`, `glyphs.yaml` | The substrate table, the fault list, the change log, crawler policy, glyph-coverage check |
| `Resources.dc.html` | `hugo/data/resources.yaml` | All eleven categories: each entry's name, URL, description, and contact line |

**Never hand-edit the `.dc.html` file at the repo root for any of
these four pages.** It's generated output. An edit made there will be
silently overwritten the next time anyone runs `npm run build:hugo` —
`npm run check` will flag the drift ("Hugo output out of sync") but
won't tell you which side was the intended change.

A handful of one-off sentences on these pages — cross-references
between sections, framing prose that only appears once — live
directly in `hugo/layouts/*.html` instead of a data file, by design:
data files hold repeated, list-shaped content; unique editorial prose
with specific cross-page links stays in the template next to the
structure it belongs to. Editing one of these means editing a
`hugo/layouts/*.html` file directly — the same raw-HTML work described
in Tier 2 below — but the change is still safely contained to that one
sentence; regenerate and re-check the same way afterward.

### Tier 2 — Hugo-generated, but content is still raw HTML

`Manifesto.dc.html` and `Invitation.dc.html` are also built by Hugo,
but neither has a real data file behind it — checking
`hugo/layouts/manifesto.html` and `invitation.html` directly confirms
zero references to any `hugo.Data` field in either. The sixteen
theses and the Invitation's own text are written directly into the
layout template as HTML, style attributes and all, exactly like the
hand-authored pages in Tier 3. The only thing "Hugo-generated" buys
here is that the committed `.dc.html` file is still generated output —
**don't hand-edit `Manifesto.dc.html` or `Invitation.dc.html` at the
repo root either** — but the actual editing work is Tier-3-level raw
HTML, not a YAML field.

To edit either: open `hugo/layouts/manifesto.html` or `invitation.html`
directly, edit the text between tags with the same care described in
Tier 3 below, then run `npm run build:hugo && npm run build && npm run
check`.

### Tier 3 — Hand-authored pages, raw HTML, highest risk

`Home.dc.html`, `Practise.dc.html`, `Contribute.dc.html`, and
`index.html` (which must always be a byte-for-byte copy of
`Home.dc.html` — see below) are **not** Hugo-generated. Every
paragraph is written directly as HTML, with a `style="..."` attribute
on nearly every element and no separation between the words and the
presentation. Editing a sentence means locating it inside dense,
inline-styled markup and editing it without breaking a tag or an
attribute — a real risk for anyone without HTML familiarity, and part
of why this project's own workflow requires a full rebuild-and-check
pass after every single edit to these pages, no exceptions.

These three pages are hand-authored on purpose, not by oversight: each
carries live interactive logic — a form, or (for Practise) an entire
stateful tool — through a small custom runtime (`support.js`,
sometimes called `dc-runtime`) that Hugo's static output has no way to
hold. Migrating their surrounding *prose* into the Hugo pattern while
leaving the interactive parts as-is is possible, but it's a larger,
higher-risk piece of work than any of the six pages above — see the
phased plan in `tasks.md` (search for "Hugo migration, phase 2") for
how that would actually be scoped.

**If you need to edit one of these four pages:**

1. Locate the exact sentence in the file (all four are single files at
   the repo root).
2. Edit only the text between tags — never remove or duplicate a `<`,
   `>`, or a quote mark around a `style` attribute.
3. If you edited `Home.dc.html`, also run:
   ```
   cp Home.dc.html index.html
   ```
   `index.html` must stay byte-identical to `Home.dc.html` — `npm run
   check` verifies this and will fail if the two drift.
4. Run `npm run build && npm run check`. Both must pass clean.
5. If you're not confident reading raw HTML, have someone who is
   review the diff before it ships — a broken tag can silently drop
   content or break the page for screen-reader users without ever
   throwing a visible error in a browser.

## The verification pass, every time

Regardless of which kind of page was touched, nothing ships without
all three of these passing clean, in this order:

```
npm run build:hugo   # only needed if a hugo/ file changed
npm run build         # regenerates the no-JS prerendered copies
npm run check          # HTML validation, accessibility, CSP, and
                        # Hugo-output-sync checks
```

`npm run check` is the one that actually catches mistakes — broken
markup, a missing alt attribute, a link that violates the site's
content-security policy, or (for the six Hugo pages) generated output
that no longer matches what's committed. Treat a failure here as
blocking, not advisory.

## Why the split exists, and what would close it

RS-004 (see `completed.tasks.md`) moved five pages onto the Hugo build
step, mainly to give this project a real generator instead of hand-
authored HTML everywhere (see `docs/spec/decision-record-d1-d15.md`
D2). Three of those five — Learn, Archive, BehindTheScenes — also got
their actual content extracted into data files as part of that same
work, which is what makes them genuinely safe to edit without reading
HTML. Manifesto and Invitation moved onto the build step but kept
their prose embedded in the template, so Tier 2 is exactly as real a
gap as Tier 3 for someone without HTML experience, even though the
`.dc.html` file happens to be generated rather than committed by hand.
This task extended the "actually data-driven" set to a fourth page,
Resources.

Two gaps remain, and they're different kinds of gap:

- **Manifesto and Invitation's prose could move into data files** with
  effort roughly comparable to what Resources just took — both are
  static reading content with no interactive logic, the same shape
  Learn/Archive/BehindTheScenes/Resources already prove out. Not
  attempted here since it wasn't part of what was asked, but a
  reasonable next low-risk task if closing Tier 2 matters.
- **Home, Practise, and Contribute's prose is harder to extract**,
  because each page interleaves it with real interactive logic — a
  live form, a stateful tool — that a rushed migration could quietly
  break in ways this project's own automated checks might not catch.
  This is tracked as its own phased piece of work in `tasks.md`
  (search for "Hugo migration, phase 2"), not attempted here. See that
  plan for the reasoning and the proposed phases.
